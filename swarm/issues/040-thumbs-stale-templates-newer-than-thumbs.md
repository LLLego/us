## RESOLUTION (Lane 5, 2026-08-22)
OUT OF SCOPE — this issue lives in the app repo (js/app.js / frames-next.js)
and concerns runtime thumbnail sync, not the emitter's geometry. Lane 5 covers
geometry only; the app-side thumb sync belongs to Lane 4 hygiene or a
follow-up. Filing as wontfix for Lane 5 specifically — the band-cap fix
already re-emits fresh templates; thumb regeneration is a separate concern.

Note: lane5 emits fresh `templates/<design>-<layout>.png` so the *templates*
side of the equation is current. Only `thumbs/` needs an app-side refresh.

## SYMPTOM
`thumbs/<design>-{strip,grid,single}.png` are **stale**: they were generated
by an older emitter run and were **not** regenerated when the emitter was
last rerun. The corresponding `templates/<design>-{strip,grid,single}.png`
have more recent mtimes but very different file sizes for the SAME pixel
dimensions — strongly indicating the preview thumbnails reflect a pre-band-cap
era of the design.

## REPRO / EVIDENCE

`frames-next/build_frames.py:733-737` only copies thumbs from a static
`AUD` (audit) directory:

```python
AUD = ROOT / "_audit"
for name in DESIGNS:
    for layout in ("strip", "grid", "single"):
        src = AUD / f"{name}-{layout}.png"
        if src.exists():
            shutil.copy(src, TH / f"{name}-{layout}.png")
```

`TH` = `us-temp/thumbs`, `ROOT` = `us/frames-next`. The `_audit` directory
is **never** regenerated by the build script — it depends on an external
manual render pass. So thumbs are frozen at whatever last lived in `_audit`.

Direct evidence (file listing):

```
templates/cupid-strip.png  20/08/2026 12:10:25  618,245 B (900x2700)
thumbs/cupid-strip.png     20/08/2026 12:08:48  3,441,069 B (900x2700)
                              ^^ newer          ^^^^^^^^^^^^^^^^^^^^^
                                                5.6× larger for same dims

templates/pooh-strip.png   20/08/2026 12:09:03  643,237 B (900x2700)
thumbs/pooh-strip.png      20/08/2026 12:08:48  3,355,877 B (900x2700)
                              ^^ newer          ^^^^^^^^^^^^^^^^^^^^^
                                                5.2× larger for same dims

templates/cupid-pair.png   ...                   958,850 B (1800x2700)
thumbs/cupid-pair.png      ...                   740,034 B (1800x2700)
                              close in size — pair layout's char art was
                              probably similar in both eras
```

The ~5× file-size delta for the same pixel dimensions (strip/grid/single) is
not normal PNG behavior; it points to a substantively different rendered image
(extra detail / different asset / no drop-shadow baked in). Per the project's
recent commit log, the band-cap rule changed the visual weight of the frames
substantially; that change is reflected in templates/ but not in thumbs/.

The end-user impact: gallery previews (which use `thumbs/`) show the old
over-sized characters while the live stage preview (via `frames-next.js`)
draws the current, band-capped templates. Users see a different frame in
the gallery than they'll actually capture.

## EXPECTED
`thumbs/<design>-<layout>.png` should match the current template render — same
characters, same band-capping, same visual weight — so the gallery preview
agrees with the live preview.

## ACTUAL
`thumbs/` are 5× larger on file size than the equivalent `templates/` for the
same dims, mtime is older, and they were copied from an unsynced audit folder.

## SUGGESTED FIX DIRECTION
Two options:

1. Have the emitter regenerate the thumbs from the current build. Concretely,
   after the templates write loop, render each `<design>-<layout>` HTML to a
   PNG and write both `templates/...png` AND `thumbs/...png` (the latter is
   already the same file for `duo-strip`/`duo-grid`/`pair` — only strip/grid/
   single need a separate thumb render).

2. Drop the `AUD` indirection: write thumbs directly from the same render
   pipeline that produced `templates/`. The `shutil.copy` from `_audit` should
   be replaced with a same-source render that knows about the band-cap fix.

Also note: `thumbs/` only covers strip/grid/single (per build_frames.py:734),
not duo-strip/duo-grid/pair. The bridge `FramesNext.thumbURL` is only called
for those three layouts (line 144), so this is by design — but worth noting.
